- (decision) Stakes: solo personal production tool + portfolio piece; PRD scoped for downstream agents (detailed)
- (decision) Working mode: Coaching path, Vision + Features entry point
- (decision) Conchita persona: 90s old-school accountant, ironic tone, Pepper Potts archetype — competent, slightly sharp, never generic finance-app cheerful
- (decision) Success definition: unconscious daily logging habit + casual couch-browsing analytics + data trust (correct small mistakes only) + reliable historical data for family economy analysis
- (decision) Portfolio audience: recruiters/hiring managers — must signal production-readiness: tests, CI/CD, strong TypeScript, minimal dependencies, professional completeness
- (assumption) Family economy: Marc logs solo but data represents household finances (not just personal), implying multi-category family spend tracking is a real use case
- (decision) V1 user: Marc only. Near-future: partner added as second user. Architecture must not block multi-user but V1 does not build it.
- (decision) Habit success signal: logging immediately after receipt or leaving the place (point-of-purchase behavior)
- (decision) Trust threshold: max 1-2 manual corrections per week. Gmail invoice entries fully trusted (zero correction expected).
- (decision) Portfolio goal: repo forks + demo invites from recruiters. License protection needed (no commercial copying). Demo-quality bar.
- (decision) Widget confirmation: shows mini confirmation inline after Conchita round-trip. If app is backgrounded/closed, push notification fires; tap opens edit card in app.
- (decision) Photo/PDF entry: passes through existing n8n flow unchanged. App handles camera/file capture natively, sends to same endpoint as Telegram.
- (decision) Offline handling: queue entries locally (Telegram-style), auto-send on reconnect. V1 only needs to handle a couple of queued entries — no bulk offline sync needed.
- (decision) Confirmation card required fields: amount, category, subcategory, description, context. Currency and date added only if screen real estate allows without crowding.
- (decision) Drum rollers apply to closed/finite lists: category, subcategory (from SQL), currency if shown. Open fields (description, amount) are text input only.
- (decision) Full edit screen: all fields including date (native date picker). Drum rollers maintained for closed fields for consistency.
- (decision) Delete: only from list (swipe-to-reveal) or from full edit screen — always with confirmation dialog. Not available directly from confirmation card.
- (assumption) DB schema has both category and subcategory fields — both surfaced in confirmation card and edit screen drum rollers
- (decision) List item fields: amount (dominant), category (secondary), subcategory (tertiary), short date if space allows. Exact layout is UX call.
- (decision) Home screen window options: last week (Mon–Sun), last month (calendar), last 7 days, last 30 days — user-configured in Settings. Total shown = sum of what's visible in list.
- (decision) Post-log list update: list source of truth is Conchita's confirmed response, not Marc's raw input. When app opens after background logging, entries cascade bottom-to-top (oldest→newest), fast with subtle stagger between items. List must refresh from backend on Conchita confirmation — not from local input.
- (assumption) List refresh mechanism: app needs a push/polling strategy to receive Conchita-confirmed data. Architecture must define this — PRD flags it as a constraint.
- (decision) Analytics: unified filter bar at top (not just time selector). Filter dimensions: time span, category, subcategory, context. Quick pills (last month / last week) adjacent to filter button — to discuss with UX.
- (decision) Graph types in V1: donut, pie, bar (swipeable). UX may propose additional types if descriptively valid.
- (decision) Analytics manual deselect: local-only view tweak, not persisted. Resets on next Analytics session open.
- (decision) Analytics data flow: app sends raw filter params to n8n agent; backend generates SQL, aggregates, returns structured data. No client-side aggregation.
- (decision) Context UI: no dedicated screen. View/pick active context = fast access from home screen. Create/archive/unarchive/delete = Settings (modal or secondary screen). UX to confirm exact placement. App maintains 3 main screens max.
- (decision) Retroactive bulk context assign: deferred from V1. V1 only supports context change via individual entry edit. Bulk edit is an open question for later.
- (decision) Gmail invoice card: identical to regular confirmation card (amount, category, subcategory, date, context, etc.) plus associated PDF file. PDF accessible via swipe-sideways on the entry alongside edit/delete. UX to refine swipe-reveal pattern.
- (decision) Unknown sender: Marc can add the sender directly from the notification/review card (quick inline action). Settings also has full senders management (add/edit/delete known senders).
- (decision) Settings / connection: all credentials needed to connect a personal n8n instance go in Settings. Self-hosting pattern: any user can point the app at their own n8n instance via Settings. Exact fields (URL, token, webhook secret, etc.) are architecture decisions.
- (decision) Theme: dark/light mode only. Typewriter font scope (everywhere vs Conchita voice copy only) is a UX decision.
- (assumption) Self-hosting is a first-class use case: the app + n8n repo should be packageable for a technically able second user to run independently. This shapes repo documentation requirements.
- (decision) TypeScript: strict mode. Husky pre-commit hook enforces lint + type check before every commit.
- (decision) Testing: unit + component + E2E (Detox or similar). Meaningful coverage on critical paths — no fixed percentage. Marc decides coverage threshold.
- (decision) CI/CD: PR → lint + type check + tests (must pass to merge). Merge to main → GitHub Actions builds and stores artifact locally for download. No TestFlight or store deployment.
- (decision) Dependencies: Zustand confirmed. React Native Reanimated — architect decides if truly warranted. All other dependencies: only if genuinely needed.
- (decision) V1.1 explicit roadmap: (1) voice entry, (2) multi-user with partner access only. Both deferred from V1 but named as next.

- (event) PRD finalized: status set to final. All finalization steps complete — memlog audit, input reconciliation, rubric review, fix pass, prose polish, structure polish.
